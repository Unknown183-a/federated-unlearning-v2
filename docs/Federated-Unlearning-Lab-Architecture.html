Chapter 00 — Why This Exists

Purpose & Product Vision

Not a collection of accuracy tables. A laboratory a professor can watch, end to end, and understand without reading a line of source code.

This document specifies an interactive Federated Learning + Machine Unlearning Dashboard. It turns an existing research pipeline into a visual demonstration that makes the entire research story visible in one continuous path:

fig 00.1 — the one path every chapter in this document opens upCh.00

The central question the dashboard exists to answer, stated in the professor's own words:

Central Question "Can we remove the influence of one federated client from an already-trained global model — without retraining the entire federated system from scratch?"

Two constraints shape everything downstream. First, training must not be required live — it can be performed offline and the resulting global model or checkpoints loaded on demand. Second, unlearning should be executable live when possible — the forgetting step is the part worth watching happen, so it is the part the architecture protects hardest.

What the dashboard must make visible

The Data Story

Which dataset, how it's split across clients, and what each client owns.

The Training Story

How local training happens and how FedAvg aggregates it into a global model.

The Forgetting Story

Which client is targeted, how Gradient Ascent removes it, how Knowledge Distillation preserves everything else.

The Proof

Whether the target client's information was actually forgotten — measured, not asserted.

The Comparison

How the unlearned model stacks up against the original, and against a full retrain.

The Cost

How long unlearning takes relative to retraining from scratch.

Chapter 06 — The Hinge Point

Trained Global Model & Target Client Selection

Everything before this chapter built a model. Everything after this chapter tries to make it forget something. This is the screen where the audience picks what.

Trained global model summary

Unlearning Engine›Overview & Timeline
Chapter 07 — What "Unlearning" Means Here

Unlearning Overview & Status Timeline

Two stages, always shown in the same order, with a visible status timeline connecting them.

fig 07.1 — forget first, then repair — never the other orderCh.07

Gradient Ascent pushes the model away from the target client's data — increasing its loss on that client specifically, so its influence is actively unlearned rather than merely diluted. Knowledge Distillation then repairs collateral damage, using the pre-unlearning model as a teacher so accuracy on every retained client is preserved as closely as possible.

Unlearning Engine›Gradient Ascent
Chapter 08 — Actively Forgetting

Gradient Ascent

The step that does the actual forgetting — and the one the dashboard must narrate most carefully, because "increasing loss on purpose" looks like a bug unless it's explained as one.

fig 08.1 — target-client loss climbs on purpose, then Knowledge Distillation pulls it back down for everyone elseCh.08

Interpretation, in plain language

What's happening

The model is nudged, step by step, to perform worse specifically on the target client's data — the opposite of normal training, applied narrowly.

Why it's not a bug

Rising loss on the target client, with the rest of the model still shown as stable, is the visible signature of forgetting actually taking effect.

Unlearning Engine›Distillation & Live Replay
Chapter 09 — Repairing the Damage

Knowledge Distillation & Live Unlearning Animation

Gradient Ascent is deliberately destructive. Knowledge Distillation is what makes the destruction selective.

fig 09.1 — the teacher supplies everything the student is not supposed to forgetCh.09

Knowledge Distillation graph

A per-retained-client accuracy chart, before and after distillation, to show recovery visually rather than asserting it in a sentence.

Live unlearning animation

During an actual live run, the dashboard animates the two-stage pipeline in real time: a moving indicator on the Gradient Ascent step, followed by one on Knowledge Distillation, each tied to genuine progress from the backend — never a fake progress bar (Ch.18, Ch.26).

Unlearning Engine›Unlearned Model & Evaluation
Chapter 10 — The Result, Measured

Unlearned Model & Final Evaluation

The unlearned model is presented the same way the global model was in Chapter 06 — as a first-class object — then put through the same battery of tests the whole document has been building toward.

Metrics evaluated

MetricWhat it answers
Global Model AccuracyDid overall performance survive unlearning?
Forget-Client AccuracyDid performance on the target client actually drop?
Retained-Client PerformanceDid every other client's accuracy stay intact?
Membership Inference Attack (MIA)Can an attacker still tell the target client's data was ever used?
RuntimeHow long did unlearning take, end to end?
Why MIA matters mostAccuracy dropping on the target client is necessary but not sufficient proof of forgetting. The Membership Inference Attack is the closest thing this pipeline has to direct evidence that the target client's fingerprint is actually gone from the model.

Chapter 11 — Proving It Was Worth Doing

Before vs After vs Full Retraining

Unlearning is only interesting relative to two baselines: the original model, and the "just retrain everything" alternative it's trying to avoid.

Before / After visualization

Every metric from Chapter 10 shown twice, side by side — original global model, and unlearned model — so the trade-off is visible at a glance rather than buried in two separate screens.

Full retraining baseline

A federated model retrained from scratch, excluding the target client entirely, computed once (typically offline) and stored as the ground-truth comparison point.

Runtime comparison

ApproachRelative cost
Full Retraining (exclude target client)Full federated training cost — every round, every client, again
Gradient Ascent + Knowledge DistillationA small fraction of that — the entire pitch of unlearning as an approach
The whole point of the dashboardIf unlearning didn't cost meaningfully less than retraining, there would be no reason to demonstrate it. This chapter's chart is the one a skeptical professor will look at first.

Backend Services›Live vs Precomputed
Chapter 18 — Two Speeds, One Interface

Live vs Precomputed Strategy & Demo Mode

Federated training is expensive; unlearning is cheap. The dashboard treats them differently on purpose.

StageDefault strategyLive option
Federated TrainingLoad from a precomputed experimentRun live when time allows
UnlearningRun live whenever possibleFall back to a stored replay only if compute is unavailable
What must NOT happenNo screen may claim a computation is "running" or show a moving percentage unless a real computation or an explicitly labeled replay animation is actually in progress. Precomputed data is always labeled Stored Experiment or Replay Mode — never presented as if it just happened.

Demo mode for professors

A dedicated, presentation-safe mode that guarantees the full story from Chapter 12 can be told inside a 10–15 minute window even with no live compute reachable — detailed fully in Chapter 21.

Error Handling & Experiment Reproducibility

Important research comparison & success interpretation

Unlearning is judged successful when forget-client accuracy drops meaningfully, retained-client accuracy stays close to the original, MIA performance moves toward chance, and the runtime stays a small fraction of full retraining — all four together, not any single metric alone.

Dataset-specific behavior

CIFAR-100's 100 classes change how the heatmap (Ch.04) and per-client dominant-class lists render, but never change the pipeline itself — the same nine pages, the same nine artifacts.

Closing›Final Architecture Summary
Chapter 24 — One Picture, Everything In It

Final Architecture Summary & Two Entry Points

Both modes from Chapter 01, both compressed into the single research story from Chapter 12, both governed by one source-of-truth rule.

Source-of-truth ruleWhatever the Compute Manager (Ch.25) actually returns is what the dashboard shows — never a value invented, estimated, or interpolated on the frontend. If a number isn't available from the backend, the screen shows that it's unavailable, not a placeholder that looks real.

Final acceptance checklist

  • Dataset, experiment setup, and data distribution stages are all visible and dynamic
  • Federated learning is shown as a real client/server loop with round-by-round metrics
  • Target client selection and unlearning are shown as two distinct, honestly-labeled stages
  • Evaluation includes accuracy, forget-client accuracy, retained-client accuracy, MIA, and runtime
  • Before/after and full-retraining comparisons are both present
  • The Quick Demo works end to end from a stored model
  • The full research story replays identically from precomputed artifacts

Compute Infrastructure›Fallback, Security & Acceptance
Chapter 26 — What Keeps the Demo Honest and Safe

Failure, Fallback, Security & Acceptance Criteria

The closing chapter: what happens when compute fails mid-demo, what the frontend must never be allowed to touch, and the checklist that defines this layer as done.

Failure and automatic fallback

fig 26.1 — a failure is always narrated, never hiddenCh.26

If automatic fallback triggers, the dashboard says so plainly — "College GPU unavailable. Switched to Demo / Precomputed mode." — because the user must always know which backend actually produced what's on screen. No live-looking indicator (GPU Running… Gradient Ascent: 72%) is ever shown unless a real computation is behind it; precomputed data is always labeled Stored Experiment, Replay Mode, or Experiment Replay instead.

Environment information & shared artifact strategy

An optional environment panel can surface dataset, clients, model, backend, device, and experiment ID together — and every backend saves its outputs in the same backend-independent formats (JSON, CSV, PyTorch checkpoints, NumPy arrays), so the dashboard consumes one result schema no matter which machine produced it.

Recommended backend priority

College GPU → Google Colab GPU → Local Mac (MPS/CPU) → Demo/Precomputed — reflected exactly in Auto mode, matching the diagram in Chapter 25.

Security requirements

Never in frontend HTML/JavaScriptSSH passwords or private keys, college GPU credentials, API secrets, or cloud credentials of any kind. All credentials stay server-side; the dashboard talks only to a controlled backend API, never to the college server's SSH layer directly.

Acceptance criteria for compute architecture

  • A Compute Backend selector exists, and Auto is available
  • College GPU can be configured as the primary live backend
  • Google Colab is usable as a temporary GPU backend
  • Local Mac MPS/CPU execution is supported for lightweight experiments
  • Demo/Precomputed mode is always available
  • Backend status and the active backend during unlearning are both visible
  • Backend failures produce clear messages; fallback never fabricates results
  • Stored experiments are clearly labeled at all times
  • One dashboard visualization layer works across every backend type
  • Credentials are never exposed to the frontend
  • The professor demonstration can continue even when the college GPU is unavailable
End of documentThis closes the loop opened in Chapter 00: a dashboard that can tell the complete federated-unlearning story, live when possible, honestly labeled when not, and never dependent on a single machine being awake.
